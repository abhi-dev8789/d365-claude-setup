# Global rules — Power Platform / Dynamics 365 work

These are operating rules, not background reading. They exist because each one corresponds to
a failure that has already happened in real work.

No org URLs, environment GUIDs, tenant IDs, publisher prefixes or client names belong in this
file. Environment-specific detail lives in per-project config. Keep it that way — this file is
version-controlled and shared across client engagements.

---

## 1. Verify against Microsoft Learn, never from memory

Before answering any question about Power Platform, Dataverse, Dynamics 365 APIs, `pac` CLI
syntax, or SDK types — **query the `microsoft-learn` MCP server first.**

This platform deprecates aggressively and the public web is full of blog posts written against
versions that no longer exist. Training data is a snapshot; Learn is refreshed daily.

- If Learn and a web search result disagree, **Learn wins.**
- If Learn has no answer, say so explicitly rather than filling the gap from memory.
- When you state an API signature, a CLI flag or a limit, you should be able to name the Learn
  page it came from.

## 2. Do not claim something is impossible without checking

Never tell the user a Power Platform task "can't be automated", "has to be done manually in the
maker portal", or "isn't supported" until you have:

1. queried the `microsoft-learn` MCP server, **and**
2. checked the installed skills — `dv-metadata` (tables, columns, relationships, forms, views),
   `dv-solution`, `dv-security`, `dv-admin`, the `model-apps` and `power-automate` skills.

This rule exists because of a specific incident: Dataverse entity and field creation was
declared impossible to automate, the user pushed back, and it was then done successfully. The
capability was there; the check wasn't. An unverified impossibility claim costs more than a
wrong answer, because the user stops asking.

If you genuinely cannot find a way, say **"I couldn't find a supported way to do X — here's
what I checked"** and list the sources. That is a different claim from "it's not possible."

## 3. Deprecated APIs — do not emit these

| Do not use | Use instead |
|---|---|
| `Xrm.Page` | `executionContext.getFormContext()` |
| `OrganizationServiceProxy`, `CrmServiceClient` | `ServiceClient` (`Microsoft.PowerPlatform.Dataverse.Client`) |
| 2011 SOAP endpoint | Dataverse Web API (OData v4) |
| `Microsoft.Xrm.Sdk` from the legacy CRM SDK download | the NuGet packages |
| `Xrm.Utility.openEntityForm` for new work | `Xrm.Navigation.navigateTo` |
| Synchronous `XMLHttpRequest` in web resources | `fetch` / async Web API calls |
| Classic workflows for new logic | Power Automate flows, or Custom API + plugin |

If you find yourself writing one of these, stop and look up the current equivalent.

## 4. Verify deployment results — exit code 0 is not success

After any import, publish, push or deploy, **confirm the actual state** before reporting.

- Solution import → `pac solution list` and check version and the managed/unmanaged flag.
- Publish → confirm publish completed, not merely that the command returned.
- Plugin/webresource/PCF push → read the artifact back, or check the registration.
- Data operation → query a record back.
- Flow → confirm it appears and is in the expected state.

`pac` commands exit 0 on partial success and on async operations that later fail. Report what
you actually observed. If a step failed, say so plainly and show the output — do not soften it
and do not claim completion for work you did not verify.

## 5. Canvas app gotchas (hard-won — do not relearn these)

Working with unpacked Canvas sources via `pac canvas unpack` / `pac canvas pack`:

- **`Connections.json` and `DataSources/*.json` cannot be hand-authored.** They must be
  generated by adding the data source once in Studio, then unpacking. Writing them by hand
  produces an app that packs cleanly and fails at runtime.
- **Gallery and timer `.fx.yaml` cannot be hand-authored** either — the same Studio bootstrap
  round-trip is required.
- The workflow that actually works: create a skeleton in Studio with the data sources and any
  gallery/timer controls wired up → `pac canvas unpack` → edit the YAML → `pac canvas pack` →
  reimport.
- Plan for this round-trip up front rather than discovering it after a failed pack.

## 6. Solution hygiene

- Always work inside a **named solution with an explicit publisher prefix**. Never author into
  the Default solution — it cannot be exported cleanly and makes ALM impossible later.
- Ask which solution and publisher to use if it is not already established in the project.
- Prefer unmanaged in dev, managed downstream.
- Components referenced across solutions need explicit dependency handling — check before
  assuming an export is complete.

## 7. Environment safety

A status line shows the active Dataverse environment on every prompt, and a `PreToolUse` hook
blocks destructive `pac` commands aimed at environments not listed in
`~/.claude/dev-environments.txt`. `bootstrap.ps1` generates that file pre-filled with the
machine's `pac auth` profiles, every line commented out.

The line to hold: **creating or scaffolding that file is fine — uncommenting or adding an entry
is not.** Choosing which environments are safe is the user's decision. A guard the agent can
widen protects nothing.

So if the hook blocks you: name the environment that was about to be modified, say which line
in the allowlist would permit it, and let the user decide. Do not edit it yourself and do not
route around the hook. Work spans multiple client tenants; the guard exists because the active
auth profile is otherwise invisible.

## Working style for this domain

- **State the environment you are about to touch** before any write operation.
- **Prefer `pac` CLI and the installed skills over hand-rolled scripts.** If a skill covers the
  task, use it — that's why it's installed.
- When something fails, read the actual error. Dataverse errors are verbose but specific;
  the useful detail is usually several lines in, not in the first line.
- Plugin trace logs and flow run history are the real diagnostics. Reach for them before
  theorising about a failure.
